# 스펙 받아 구현하기

스펙은 "무엇을" 의 결정이고, "어떻게" 는 CLAUDE.md 의 규칙을 따른다.

1. `_specs\<파일>.md` 를 끝까지 읽는다. 특히 **수용 기준·비범위·열린 질문**.
   - 스펙이 CLAUDE.md 규칙(`nav.js` GROUPS·sitemap 갱신, 광고 자리 순서, 상표명 금지,
     법정 수치 출처 확인 등)과 충돌하면 규칙을 따르고 리포트에 적는다.
   - 수용 기준이 모호해 구현 방향이 크게 갈리면 먼저 묻는다.
     작은 모호함은 스스로 정하고 리포트 "임의 결정" 에 적는다.

2. 관련 코드를 읽고 구현 계획을 2~4줄로 보고한 뒤 구현한다. **비범위 항목은 건드리지 않는다.**

3. CLAUDE.md B절(도구 수정)·new-tool 스킬(새 도구) 절차와 자체 점검을 그대로 실행한다.

4. 수용 기준 체크리스트를 하나씩 대조한다.
   배포 후에만 확인되는 것은 "배포 후 확인 필요" 로 두고, 배포 뒤 실제로 확인해 리포트를 갱신한다.

5. 스펙 작성 시점 이후에 생긴 변화(새로 발행된 글, 새 페이지 등)로 수용 기준이 깨질 수 있으면
   깨지지 않게 처리하고 그 판단을 "임의 결정" 에 적는다.

6. `_specs\<파일>.report.md` 를 아래 형식으로 쓴다.
   (예: `2026-09-25-study-sort.md` → `2026-09-25-study-sort.report.md`)

   ```
   # 구현 리포트: <스펙 제목>
   - 스펙: _specs\<파일>.md
   - 날짜: YYYY-MM-DD
   - 커밋: 해시 7자리 또는 "미커밋"
   ## 한 일
   - 바꾼 파일과 핵심 변경 (자체 점검 결과 포함)
   ## 수용 기준 충족 여부
   - [x] 기준 — 확인 방법
   - [ ] 기준 — 미충족 이유
   - [?] 기준 — 배포 후 확인 필요
   ## 임의 결정
   - 스펙에 없어서 정한 것과 이유 (없으면 "없음")
   ## 남은 문제
   - 미해결·후속 작업 제안·기획 확인이 필요한 것 (없으면 "없음")
   ```

7. 스펙 파일(`.md`)은 고치지 않는다.
   보고는 휴대폰용으로 짧게: 수용 기준 충족 n/m, 남은 문제 한두 줄.

8. 커밋·푸시는 "올려줘" 를 받으면 CLAUDE.md D절대로(공개 리포).
   `_specs\` 는 커밋하지 않는다(`.git/info/exclude` 등록됨).
